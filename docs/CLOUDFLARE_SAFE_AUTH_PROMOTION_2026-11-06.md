# ضاديوم — خطوات نقل إصلاحات الدخول إلى Cloudflare دون تعطيل الموقع
**تاريخ المراجعة:** 6 نوفمبر 2026  
**الحالة:** خطة اعتماد قبل النشر؛ لا تعديل لإعدادات Cloudflare أو قاعدة الإنتاج.

## ما نجح بالفعل

- اختبارات PR #116 لتسجيل الدخول وتذكّر الجلسة وصفحات الأدوار وواجهة الجوال.
- محاكاة ترحيل صلاحيات قاعدة البيانات وحظر إنشاء معلم/مدرسة مباشرةً في قاعدة PostgreSQL منفصلة.
- توليد Worker حقيقي عبر OpenNext 1.20.13 وWrangler 4.154.0، وفحص الحجم و`wrangler deploy --dry-run`.
- اختبارات Workerd للصفحات العامة، ومنع الوصول غير المصرح به إلى واجهات الإدارة والمعلم والطلبات.
- اختبارات Chrome للجوال دون صلاحيات حقيقية.

## إعداد Cloudflare الصحيح — لا تطبقه على الإنتاج الآن

تنص وثائق Cloudflare الحالية على أن **Workers Builds لا يطبّق إعداد `build.command` الموجود داخل Wrangler**، وأن أمر البناء وأمر النشر حقلان مستقلان في لوحة التحكم:
https://developers.cloudflare.com/workers/ci-cd/builds/configuration/

في **عامل اختبار منفصل** مربوط بفرع PR #121، وبعد التحقق من عدم وجود مسارات إنتاجية أو دومينات حية:

| الحقل | القيمة |
| --- | --- |
| جذر المشروع | `/` |
| فرع Git | `fix/dadyoom-auth-opennext-preview-20261106` |
| Build command | `npm run cloudflare:build` |
| Deploy command | `npx wrangler deploy` |
| Preview command (إن استُخدم) | `npx wrangler preview` |
| Worker name | `dadyoom-auth-preview` |
| Production custom domain | لا تربط `dadyoom.com` بعامل الاختبار |

الأمر `bun run preview:vinext` غير موجود في المشروع، ولا يجوز إعادة تشغيل البناء نفسه دون تغيير الإعداد الخاطئ. لا تخلط تبويب **Production** مع **Previews Base**.

**لا تنشر الفرع إلى Worker الحالي `dadyoom` قبل اكتمال الشروط أدناه.**

## ترتيب الإصدار الآمن

1. سجّل اسم الفرع الحالي الذي يخدم الموقع الحي، وأمر البناء/النشر، واسم Worker، وBindings، وأسماء الأسرار دون كشف قيمها، واحتفظ بمعرّف الإصدار المنشور للرجوع.
2. فعّل بيئة اختبار منفصلة دون أي DNS إنتاجي، واختبر بنسخ بيانات وهمية لا تتضمن بيانات طلاب.
3. تحقق في بيئة معزولة من ترحيل `supabase/migrations/20261106_p0_profile_role_request_guard.sql`، وراجع أثره على Trigger إنشاء المستخدم وRLS وسياسات المعلم والمدرسة؛ توثّق الموافقة لكل طلب.
4. اختبر تسجيل البريد، تأكيد البريد، تسجيل Google، إغلاق المتصفح وفتحه، استعادة كلمة المرور، وتصنيف الدور الحقيقي في `/my`، مع التحقق من طلب المعلم/المدرسة المعلّق.
5. اختبر منع طالب من الوصول إلى بيانات مدرس أو فصل آخر، وعودة المستخدم من الدرس إلى مساحته، والتصحيح على الخادم.
6. إذا مرت كل الخطوات، خطط لتطبيق ترحيل القاعدة مع إصدار التطبيق في فترة واحدة مع التراجع الفوري عند ظهور خطأ.
7. لا تغيّر الربط إلى `dadyoom.com` إلا بعد اختبار العامل الحقيقي والعودة إلى الإصدار المحفوظ عند الإخفاق.

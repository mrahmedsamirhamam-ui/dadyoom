# ضاديوم — لوحة تجريبية لمراجعة الصفوف 1–3 في البحرين

**النطاق:** `BH`، الصفوف 1 و2 و3 فقط. لا توجد تغييرات إنتاجية ولا اعتماد آلي ولا دمج.
**الفرع:** `feat/lesson-library-quality-phase1-20261109`.

## 1) المصدر ودقة البيانات
اللوحة تتصفح مصفوفة جرد **محلية** قادمة من:
`scripts/audit-primary-curriculum-readonly.mjs`. يجب توفير نسخة JSON محلية من `lessons`, `questions`, `activities`, `official_index`, `evidence` مع `collection_metadata`.
لا يُستنتج أن درسًا غير موجود إذا كان نطاق النسخة ناقصًا، ولا تُظهر اللوحة دروسًا افتراضية.

مثال:
```bash
node scripts/audit-primary-curriculum-readonly.mjs \
  --input=/absolute/private/path/primary-export.json \
  --output=/absolute/private/path/Audit-Matrix-Report.json
```
الملف `Audit-Matrix-Report.json` يضم `lesson_audit` (العنوان، الدولة، الصف، مسائل الأدلة الأربعة، التنبيهات التحريرية)، ولا يحتوي أي تحديث لقاعدة البيانات. لا ترفع نسخ بيانات المستخدمين إلى GitHub. تستبعد الواجهة تلقائيًا كل دولة غير البحرين وكل صف خارج 1–3.

## 2) تشغيل لوحة المراجعة محليًا
اختر مكانًا خارج `public/` وحصرًا على خادم محلي موثوق؛ لا تحفظ ملف التقرير داخل المستودع. ضع في ملف `.env.local` (لا ترفعه إلى GitHub):
```dotenv
DADYOOM_CM1_AUDIT_REPORT_PATH=/absolute/private/path/Audit-Matrix-Report.json
# افتراضيًا لا توجد كتابة: لا تضع أسرار staging حتى يتم اعتماد مخطط الاختبار
DADYOOM_CM1_STAGING_WRITES_ENABLED=false
```
ثم شغّل التطبيق محليًا باستخدام أوامر المشروع المعتادة (`npm ci` ثم `npm run dev`). افتح:
`http://localhost:3000/admin/curriculum/primary-pilot`.
يجب أن يكون المستخدم مسجلًا بصلاحية مراجع صادرة من `app_metadata.dadyoom_lesson_reviewer` وبملف `admin` ذي اسم حقيقي. دون ذلك يعيد التوجيه أو API خطأ 403.

## 3) المسارات الثلاثة
- **أخضر:** كل الأدلة الأربعة معلّمة بأنها مستوفاة **في ملف الجرد المحلي**، والمحتوى مرشح رسميًا، ولم تُرصد نواقص، والنسخة مكتملة. يُعرض زر «اعتماد كمطابق رسمي» لكنه لا ينفذ دون تحقق قاعدة staging من كل الدلائل الستة الإضافية.
- **أصفر:** رصد ادعاء أن المادة رسمية مع وجود علامة الإثراء أو عدم جاهزية المصدر. يكتب المراجع وصفًا بديلًا موثَّقًا ثم يحفظه بوصفه **مقترح تعديل**؛ لا يُغير `lessons.summary` مباشرة.
- **أحمر:** نقص في الشرح أو الأنشطة أو الوثائق أو المراجعة. «حفظ كمسودة غير مكتملة» يسجل حالة مراجعة `needs_completion`، **ولا يعدّل `lessons.status`** أو يخفي درسًا عامًا دون قرار مستقل.

## 4) كيف تعمل API؟
`GET /api/admin/curriculum/primary-pilot?lane=red&page=1` يقرأ ملف الجرد الخاص بالخادم بعد التحقق من المراجع ويعيد حتى 30 سجلًا. `POST` يتطلب ضغطة بشرية، `Origin` مطابقًا، صلاحية مراجعة، ملاحظات لا تقل عن 20 حرفًا، ومعرّف درس UUID صحيحًا، وبصمة SHA-256 للتقرير لمنع استعمال نسخة قديمة. لا يُقبل نوع إجراء غير متوافق مع قائمته.

لا تفتح الكتابة إلا **محليًا** ومع وجود قاعدة staging مختلفة فعليًا عن قاعدة الإنتاج:
```dotenv
DADYOOM_CM1_STAGING_WRITES_ENABLED=true
DADYOOM_CM1_STAGING_URL=https://YOUR-STAGING-REF.supabase.co
DADYOOM_CM1_STAGING_PROJECT_REF=YOUR-STAGING-REF
DADYOOM_CM1_STAGING_SERVICE_ROLE_KEY=STAGING_ONLY_SECRET
```
يُرفض التشغيل عند `NODE_ENV=production` أو غياب مصدر إنتاج للمقارنة أو تساوي عنوان القاعدتين، ولا تنتقل أي مفاتيح إلى المتصفح.

تستدعي API دالة واحدة فقط `dadyoom_cm1_record_primary_decision`، المقترحة في:
`docs/sql/dadyoom-cm1-primary-pilot-staging.sql`.
هذه الدالة **لم تُنفذ أو تختبر داخل PostgreSQL في هذه الجولة**، ولا يجب تطبيقها على قاعدة الإنتاج. يتطلب تطبيقها في staging المعزول أولًا مراجعة صلاحيات RLS واختبارات استرجاع/تراجع مستقلة وصحة اعتماد محاور `dadyoom_lq1_*`.

## 5) لماذا لا يكفي زر أخضر؟
قرار `VERIFIED` لا يكتب إلا في سجل `dadyoom_cm1_primary_decisions.official_syllabus_match` الخاص بمراجعة staging، وتتحقق الدالة عند الطلب من:
1. البلد `BH` والصف 1–3، وسجل منشور.
2. سجل مصدر رسمي `https` واسم المرجع والطبعة `2026-2027` والصفحة والمراجع والتاريخ.
3. شرح أصلي لا يقل عن 120 حرفًا، وملخص 30 حرفًا، وهدف واحد على الأقل، وإثبات مراجع؛ مع تطابق `lesson_updated_at` لتجنب اعتماد نسخة قديمة.
4. ثلاثة أسئلة على الأقل ونشاط منشور واحد على الأقل ودليل اختبار تشغيل موثق.
5. دليل تدقيق بشرى نهائي موثق.
6. اعتماد محاور الجودة الستة المسجلة في `dadyoom_lq1_quality_axis_reviews`.

تُحفظ عملية القرار في جدول أحداث ملحق غير مخصص للتعديل بواسطة العميل. ليس هذا استبدالًا لاعتماد الوزارة ولا يغير الدرس العام أو يولد ادعاءً مرئيًا للمستخدمين. كذلك لا يجوز استنتاج اكتمال «100%» من حضور السجلات وحدها.

## 6) متطلبات القبول قبل التفعيل
- تشغيل الاختبارات المحلية و`tsc --noEmit` وESLint و`npm run build` على النسخة الكاملة.
- إنشاء DB staging منفصلة ونسخ بيانات اختبار **مصطنعة أو منقّحة**، وتشغيل SQL بعد مراجعة مخططها.
- اختبارات حقيقية: مصادقة، رفض الدول/الصفوف خارج النطاق، رفض الأدوار غير المخولة، رفض المصدر الضعيف والنشاط الذي لم يُختبر، رفض إعادة القرار بعد الاعتماد، التزام سجل الأحداث بذرية المعاملة، وعدم تغيّر `public.lessons` قبل وبعد الضغط.
- التحقق من رفض الطلبات عبر المتصفح، ثم الاعتماد البشري **من دون دمج أو نشر تلقائي**.

**النتيجة المتوقعة في هذه المرحلة:** واجهة ومقترح API ورمز SQL مُحضّرة للفحص، لا اعتماد فعلي ولا تفعيل كتابة في الإنتاج.
